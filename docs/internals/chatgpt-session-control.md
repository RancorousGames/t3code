# T3 Code ChatGPT browser session control (local)

The custom desktop renderer retains ownership of web ChatGPT sessions. OmniMCP-Lite v0.5.8 adds one MCP tool, **`t3_sessions`**, which uses T3's existing local-only named-pipe control channel, not ChatGPT HTTP APIs or legacy OmniHub MCP forwarding.

| action     | inputs                                                                                    | result                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list`     | `which=visible` (default), `recent`, `working`, `blocked`, `all`                          | Filter ChatGPT sessions by the existing sidebar colors; returns stable ID, title, URL, `uiColor`, status/reason, heartbeat, last role/summary, and rendered turn count.                                                                                                                                                                                                                                                     |
| `read`     | `sessionId`, `from=start` or `from=end`, `count=1..20`, optional `expectedConversationId` | First or last N _rendered_ user/assistant turns. Guarded reads reject another/unknown guest conversation ID.                                                                                                                                                                                                                                                                                                                |
| `send`     | `sessionId`, `message`, optional `senderSessionId`, `expectedConversationId`              | Deliver a follow-up using the embedded ChatGPT composer. Guarded sends only type/click within the expected conversation. An optional source ID is caller-reported (not authenticated); the guest receives source/recipient IDs in its message. Reports `delivery=user_turn_observed` only after the new user turn appears in the rendered DOM, not after assistant acknowledgement/completion. Never retries after a click. |
| `complete` | `sessionId`                                                                               | Explicitly declare this browser session finished with its current task. Caller-reported (local socket is not authenticated per ChatGPT guest), retained in browser-local session metadata with conversation URL and observed turn count. A later new user turn invalidates the marker. This is distinct from merely appearing idle.                                                                                         |
| `reload`   | `sessionId`, optional `force`                                                             | Refreshes a session with the exact load-failure panel or the interrupted-connection banner (`stuck_connecting`), rechecking the transient banner before refreshing. `force=true` permits refresh of other non-working sessions, but **never** while positively classified as generating. No automatic refreshing of interrupted connections; they sometimes reconnect on their own.                                         |

A **turn** is a user message and its following assistant reply(s); tool responses aren't separate turns. Per-message text is currently limited to 6,000 characters, and `count` to 20. The reader accesses only messages mounted in the current guest DOM; if ChatGPT has virtualized older history, it cannot guarantee full retrieval. Hidden sessions are reported, not activated or inspected.

The sidebar's 2-second activity poll inspects a mounted ChatGPT guest even when the navigation overlay says `Loading`: the guest may already show its own conversation-failure panel. Stalled JavaScript inspections time out after 4 seconds and are retried. A visible `Could not load this ChatGPT conversation` panel with Retry is red without manually refreshing the page; missing composer controls during initial hydration remain unknown until loading finishes.\n\nThe list `which` filters use the sidebar's exact color classification, which is different from task completion: `visible` includes all non-hidden sessions; `recent` selects blue sessions (now idle, but observed working within the last **15 minutes**); `working` selects green sessions with an active Stop control; `blocked` selects both orange (`interrupted`) and red (`invalid`) sessions; `all` includes hidden sessions (whose color is unknown). Hidden sessions are never inspected or restored merely to list them. `total` counts only matching entries.

The session result also includes optional `parentSessionId` and `project` metadata. The ChatGPT sidebar groups using T3's registered project names and an offline-learned workspace-filename frequency model (`apps/web/src/chatGPTGroupingTraining.generated.json`), supplemented by user-confirmed labeled sessions. For nonregistered names it clusters repeated, properly cased terms, avoiding incidental lowercase words such as `using`. No growing project-specific hardcoded keyword list is required. The model can abstain on ambiguous titles. The source training snapshot, user ground truth, and offline Python evaluator live in `.t3/grouping-lab/`; `python scripts/chatgpt_grouping_lab.py --index-workspaces --export-web --annotate` regenerates the locally compiled training asset without changing the live T3 session profile. Only environment-scoped persisted parent metadata establishes parent links; offline project-training fixtures can never establish ancestry, even when the IDs match. A child is indented beneath its parent, but titles, project similarity and build-global historical annotations never invent links. Project headers can be collapsed, and activity sorting remains cross-project. Grouping is browser-local UI metadata, not an OpenAI/ChatGPT session relationship API.

To spawn a reliably nested child, supply `parent_session_id` to the OmniMCP `spawn_chatgpt_subagent` tool or `--parent-session-id ID` to `scripts/spawn-chatgpt-session.mjs`. Once the updated OmniMCP binary is deployed, its tool rejects a spawn unless you supply exactly one of `parent_session_id` (nested child) or `root_session=true` (intentional root), instead of silently orphaning an intended child. Once the updated T3 renderer is rebuilt and restarted, it injects the newly created session's own persisted T3 UUID and its explicitly linked parent into that guest's *first* ChatGPT prompt, together with an addressable `t3_sessions(action=send)` reporting route; descendants can therefore use their exact own UUID as `parent_session_id` on further spawns. This handoff is routing metadata, not proof of caller identity. Previously existing manual ChatGPT sessions still require their exact T3 ID to be supplied explicitly. For CLI callers that must spawn _only_ a child, pass `--require-parent` as well; it refuses to spawn if `--parent-session-id` is missing. This avoids creating an unintended new root after a lost tool-caller identity. `t3_sessions list` exposes T3 IDs but does **not** identify which ID belongs to the invoking ChatGPT conversation; the caller needs its own exact T3 ID from a trusted handoff, not from title or activity heuristics. The same applies to managers spawning children and children spawning grandchildren. Optionally supply `project` / `--project NAME` to identify the corresponding T3 project, including by workspace path. An omitted parent ID leaves the new session top-level: the OMCP/CLI local socket has **no reliable identity of the invoking web ChatGPT tab**. Reproduced on 2026-10-18 by `mcp__OMCP__spawn_chatgpt_subagent` reporting `parent=none (no explicit caller identity)` even when invoked from an embedded manager ChatGPT session. The missing provenance originates _before_ T3 receives the spawn command; no T3 renderer grouping fix can recover it. Do not infer ancestry from active tabs, routes, most recent clicks, activity or project titles: all can refer to unrelated conversations. The caller must first discover its own T3 browser UUID via `t3_sessions` / the sidebar and pass that UUID as `parent_session_id` or `--parent-session-id`. The `project` argument is only a project hint, not lineage proof. An explicit unknown/hidden parent is rejected; renaming preserves metadata, and closing a parent detaches its children. A ChatGPT `https://chatgpt.com/c/...` conversation URL is **not** this UUID. `list` and `read` also return a separate, nullable, URL-derived `conversationId` (the `/c/<id>` token); the same browser tab UUID can point to another conversation or another website after navigation, and a new chat may have no conversation ID yet. No provider API guarantees the permanence of that URL form. OpenRig should treat the tab/session UUID as a T3 control handle, not as universal conversation identity. Session IDs and parent links persist in the environment-scoped browser localStorage across renderer/app restarts; explicit detach markers are preserved so historical training labels cannot re-parent them.

The returned statuses are observation-based, not a provider API truth source:

- `working`: visible enabled Stop generation control.
- `waiting_for_input`: generation stopped and assistant's final visible text ends in a question mark (heuristic only).
- `done_or_idle`: assistant last replied and generation has stopped; does _not_ prove the task is finished.
- `pending_or_stalled`: last visible message is from user but the generation control is absent.
- `stuck`: existing T3 recovery detector confirms exact ChatGPT load-error plus Retry button.
- `stuck_connecting`: visible `Connection interrupted. Waiting for the complete answer` notice; ChatGPT may recover spontaneously or require a manual `reload`. This takes precedence over a stale Stop button. `statusReason` includes a UTC observation timestamp. The structured `statusObservedAt` field records the most recent inspection, while `connectionInterruptedFirstSeenAt` is the first time **this running T3 app** observed the notice, not necessarily when the connection actually dropped. It resets after a successful non-interrupted inspection.
- `hibernated`: the guest was unloaded to save memory because it sat on a conversation, unshown and not working, for 15 minutes (each guest is a separate 0.4–1 GB renderer). `list` reports it without reloading; `read`, `send`, `reload`, `complete` and `archive` reload it first and wait up to 45 s for the composer. Selecting it in the sidebar also reloads it.
- `loading`, `new`, `unavailable`: no reliable answer (unmounted, hidden, authentication error, no readable messages, etc.).

**Examples** (first eight requests use the installed `t3_sessions` MCP action; the final two require the direct CLI until the OmniMCP tool schema is updated):

```json
{"action":"list","which":"visible"}
{"action":"list","which":"recent"}
{"action":"list","which":"working"}
{"action":"list","which":"blocked"}
{"action":"list","which":"all"}
{"action":"read","sessionId":"<id from list>","from":"end","count":3}
{"action":"read","sessionId":"<id from list>","from":"start","count":1}
{"action":"send","sessionId":"<id from list>","message":"Please report your current progress."}
{"action":"reload","sessionId":"<id from list>"}
{"action":"send","senderSessionId":"<source T3 UUID>","sessionId":"<recipient T3 UUID>","message":"Review the tests."}
{"action":"complete","sessionId":"<my T3 UUID>"}
```

For **OpenRig conversation-safe routing**, pass an _optional_ `expectedConversationId` in `read` or `send`: a **lowercase canonical UUID** extracted from `https://chatgpt.com/c/<uuid>`, not a T3 browser-session UUID or full URL. Example read: `{"action":"read","sessionId":"<T3 tab UUID>","expectedConversationId":"6ad4addb-8fc0-83eb-832c-47b147adffb2"}`; guarded send uses the same field plus `message`. A guarded read requires an actually inspected guest URL; guarded send verifies that URL before touching the editor, again during typing, and **synchronously inside the guest JS task that clicks Send**, so a navigation during send-button hydration cannot reroute the message. Wrong UUID, non-ChatGPT origin, blank/new-tab URL or unavailable guest fails closed. Successful guarded responses contain `conversationGuardValidated: true` and `verifiedConversationId` to explicitly acknowledge enforcement. Unguarded legacy calls remain backward compatible.

**Old desktop compatibility is security-critical:** earlier desktop builds can ignore unknown optional protocol fields. The CLI therefore first probes guarded `read` and demands the verification acknowledgement _before_ forwarding a guarded `send`; it also demands that same acknowledgement on the send response. Custom OpenRig adapters using the local pipe directly must do equivalent capability probing and reject any response without positive guard acknowledgement. A matched `conversationId` from an unguarded old `read` is **not** sufficient. This contract is **implemented in source only until the desktop is rebuilt, restarted, and the guarded read response is verified in that running instance**; do not claim live conversation-safe sends based solely on tests or successful compilation.

Use the list/read operations for status summaries. Never assume `done_or_idle` means complete or send the same message again just because confirmation timed out. A stuck session may remain broken even after a successful refresh if the underlying ChatGPT page cannot load.

Direct CLI: `node scripts/chatgpt-sessions.mjs` accepts one JSON request on standard input and prints JSON, using the local named pipe. It also supports local `wait` with one `sessionId` or a `sessionIds` array (1–20 IDs), `mode:"any"` or `mode:"all"` (default), optional `timeoutMs` (default 30 minutes) and `pollMs` (default 3 seconds). Example: `{"action":"wait","sessionIds":["<worker1 T3 UUID>","<worker2 T3 UUID>"],"mode":"any","timeoutMs":900000}`. For one worker: `{"action":"wait","sessionId":"<worker T3 UUID>"}`. The CLI does **not** occupy a long-running desktop renderer request; it polls individual existing `read` operations, allowing other sessions to send, finish and declare completion. A successful wait requires explicit `complete` declarations; `done_or_idle` is insufficient. On timeout it returns `completed:false`, `timedOut:true`, `pending`, and `matched` rather than silently treating inactivity as completion. Completion declarations expire when the observed conversation URL changes or new turns arrive. `wait`, `complete`, and sender-labeled `send` are currently **CLI-only**; the installed OmniMCP `t3_sessions` tool still exposes only list/read/send/reload and does not yet accept `senderSessionId`, until its separate schema is upgraded. For a completion marker to be valid, the currently rendered page must be the same conversation, readable and idle, with the same observed turn count. UI navigation to other sites/conversations is not a completion signal. These are T3 ChatGPT-only controls, not the proposed cross-provider OpenRig adapter. CLI and MCP require the custom T3 Code desktop app running; they do not launch new app instances. Tests: `node --test scripts/chatgpt-sessions.test.mjs`.

## Selected-session blank URL recovery (2026-10-21; source-only)

Opening **any** existing ChatGPT session through the browser sidebar or route — already loaded, hibernated/unloaded, or restored from Hidden — now starts a targeted selected-session recovery check. Re-clicking the currently selected row starts a fresh check. If hibernated, T3 first wakes the existing exact guest; it does not create a new session. It waits for guest attachment (bounded to 45 seconds) and checks the actual inspected guest URL. If that URL is the empty ChatGPT homepage, it requires a saved canonical conversation URL and an unchanged idle/empty homepage across a short settling window. The existing `runChatGPTSessionControl({action:"reload"})` then makes two additional guest-side checks for drafts, active generation, identity and stale attachments before navigating to the saved URL. Selection cancellation is rechecked immediately before navigation. No `force` is supplied on click; ordinary healthy conversations, new chats without a retained URL, and interrupted/active/drafted pages are untouched. Background scanner cooldowns remain independent; successfully issued selected restorations record the same global recovery history. Relevant source: `apps/web/src/chatGPTSelectedSessionRecovery.ts` and `apps/web/src/components/sidebar/ChatGPTBrowserSelectionRecovery.tsx`. Focused tests: `chatGPTSelectedSessionRecovery.test.ts`, `ChatGPTBrowserSelectionRecovery.test.tsx` and `chatGPTSessionControlReload.test.ts`.

This automatic click recovery is **not running in the currently installed desktop until a coordinated T3 build/restart**. The separate existing manual recovery action was live-tested on two blank sessions and restored their original turn histories; the new automatic selection trigger is source/test verified only.

## Local conversation archive (prototype)

`node scripts/chatgpt-session-archive.mjs --watch` polls mounted, nonhidden ChatGPT sessions through the above read-only desktop pipe every 30 seconds and appends changed message revisions to `.t3/userdata/chatgpt-browser-archive/<hashed-session-id>.jsonl`, with a deduplication index alongside each journal. `--once` performs one scan; `--list-archives` lists saved sessions and their metadata without T3 running, and `--read-session ID` reconstructs the latest observed messages as JSON. Data stays on the machine and outside Git; the watcher must be started separately, it is not an auto-start desktop service. Changes to the guest-side reader require rebuilding/restarting the T3 desktop that owns the browser sessions, without disrupting active sessions until a safe restart is scheduled.

The archive deliberately preserves revisions, including partial assistant output, but is **not a guaranteed transcript**: it only sees currently mounted/DOM-rendered messages, and each archived message is bounded to 24,000 characters (ordinary `read` calls retain their 6,000-character default). A `readable=0` scan means no browser content was accessible, not a successful archive. The append-only journal is authoritative: the index is reconstructed after interrupted writes, and scans use a single-writer lock (with recovery only after its owning process has exited). Never infer task completion or full history from an unreadable session. Tests: `node --experimental-strip-types --test scripts/chatgpt-session-archive.test.mjs scripts/chatgpt-session-dom.test.mjs`.

## ChatGPT browser sidebar state and grouping

- Project matching uses the locally generated workspace filename-vocabulary asset plus user-verified labels. The browser sidebar persists a chosen project to each session's localStorage record. Loading/failed pages do not erase it. A manual project drop is authoritative and detaches the dragged session from any prior parent. `Other` is a permanent fallback/drop target.
- In Started mode, drag the status handle onto a project header to assign a session. Drop onto a session to reorder it in that group; **Shift-drop onto a session** attaches it as a child, preventing cycles. An attached child follows its parent in both Started and activity-sorted views; use the child's right-click **Detach from parent** to undo.
- Right-click a session or project for 1-hour, 1-day, 1-week or custom snooze. The Snoozed selector exposes snoozed sessions and their unsnooze controls. Snooze deadlines, group collapse state, project assignment and exact parent relationships persist across T3 restarts.
- A newly hidden session records `hiddenAt`. Hidden sessions older than **72 hours** are removed on startup and on an hourly check, with best-effort preview closure and removal of saved URL/activity metadata. Legacy hidden sessions lacking a trustworthy hiding timestamp remain untouched until restored and hidden again; no fabricated timestamps are used.
- Activity sorting places working/recent first, then inactive/unknown sessions by project, and errors at the bottom. Auto-recovery scans expanded project sessions before collapsed ones (while retaining cooldowns). Blue was adjusted slightly toward a more saturated hue.
- OMCP spawn calls should explicitly supply `parent_session_id` whenever a trusted source UUID is known. With no caller identity in the socket request, the child is deliberately kept top-level rather than nesting under whatever unrelated ChatGPT tab happens to be active.
